# 5. A GitHub App created via the manifest flow, with three access modes

Date: 2026-08-11

## Status

Accepted. Amended, see [Amendments](#amendments).

## Context and Problem Statement

Dusk reads `dusk.md` from repos, and depending on configuration it also writes to them.
It needs credentials for that, and it needs webhooks for fast reconcile.

The obvious cheap answer is a personal access token, but a PAT carries the full scope of the user's account, lives in a config file indefinitely, and cannot express per-repo consent.
The obvious robust answer is a GitHub App, but registering one has historically meant walking a user through settings pages, generating a private key, and configuring a webhook secret by hand.
That onboarding cliff is the usual reason products ship a PAT path as well.

Separately, granting write access to source repositories is a materially larger ask than granting read.
A design that treats read-only as a degraded mode will be adopted read-only anyway and will feel broken.

## Considered Options

For credentials:

1. **PAT only.**
2. **GitHub App only**, registered by hand.
3. **GitHub App only**, registered programmatically via the App Manifest flow.
4. **Both**, App for the full experience and PAT for quick start.

For write behaviour:

1. Read-only and read-write.
2. Read-only, proposal, and read-write.

## Decision Outcome

Chosen: **App only, registered via the GitHub App Manifest flow**, with **three access modes**.

Dusk registers the App on the user's behalf.
It POSTs a manifest to `https://github.com/settings/apps/new` (or `https://github.com/organizations/ORG/settings/apps/new`), GitHub redirects to Dusk's `redirect_url` with a temporary code, and Dusk exchanges it at `POST /app-manifests/{code}/conversions` for the app id, private key, and a GitHub-generated webhook secret.
The whole flow must complete within one hour.

The user's only manual step is accepting and installing.

Access modes, chosen at install time and changeable later:

- **Read**: Dusk and its agents never write to source repos. Proposed changes surface in the UI and go no further.
- **Proposal**: Dusk opens pull requests against the repo that owns the entity. The repo's own owners review changes to their own catalog entry.
- **Write**: Dusk commits directly.

All GitHub interaction goes through a single internal source interface.
GitHub is the only implementation for now, but no GitHub type crosses that boundary into the reconciler.

### Consequences

#### Good

- The manifest flow removes the onboarding cliff that normally justifies a PAT fallback, so there is exactly one credential path to document, test, and support.
- Installation tokens are short-lived and scoped to the repos the user explicitly selected, which is genuinely better security than a PAT and is visible to the user as such.
- The webhook secret is generated by GitHub during the flow, so there is no secret for the user to invent, copy, or leak.
- Proposal mode turns the larger write ask into a smaller one, and produces a better review story than direct commits: the people who own a service review changes to its catalog entry.
- A single source interface keeps a future GitLab or self-hosted implementation from requiring surgery on the reconciler.

#### Bad

- The manifest flow requires Dusk to be running and reachable at a redirect URL during setup, which adds a constraint to first-run that a pasted token would not have.
- The webhook URL is baked in at App creation. A user whose public URL later changes must edit the App, and Dusk should detect and explain that rather than failing silently.
- Registering an org-owned App requires org admin, so a user without it cannot complete setup for an organization.
- Three access modes is three code paths through the write layer, and proposal mode in particular needs PR lifecycle handling that read and write modes do not.
- App-only means no path at all for environments where creating an App is disallowed, which is a real if uncommon corporate scenario.

#### Rejected because

- PAT only was rejected on scope and consent. It grants everything the user can do, it cannot express per-repo access, and it has no natural webhook story.
- Hand-registered App only was rejected because the manifest flow exists and makes it unnecessary.
- Supporting both was rejected as surface area. The manifest flow removes the reason the fallback existed, and two credential paths means two sets of failure modes, docs, and tests for no remaining benefit.
- Two write modes was rejected because it forces the larger ask. Proposal mode is the setting most users will actually live in.

## Amendments

Amendment policy: [ADR-0028](0028-amending-adrs.md).

### 2026-08-11: "teams" to "users"

The last rejected-options entry read "the setting most teams will actually live in".
[ADR-0027](0027-design-target.md) settled the design target as a single operator, so the noun is now "users".

Terminology only.
The argument, that two write modes forces the larger ask, is unchanged.

### 2026-08-18: return after installation and start the first sweep

The manifest now carries a `setup_url`, so GitHub returns the operator to Dusk after the App is installed instead of ending the product flow on GitHub's installation page.
That page explains how to produce the first catalog result and starts a sweep immediately, which matters for a poll-only deployment whose installation webhook cannot arrive.

The URL carries the registration flow's unguessable state through a second, one-use stage.
GitHub appends an `installation_id`, but GitHub documents that this parameter is spoofable, so it is never treated as authority to spend the installation's API budget.
The post-install state is held in memory and expires with the manifest flow after an hour; a restart can lose the automatic sweep, but the poll floor still guarantees eventual reconciliation.

This completes the one manual sequence the original decision intended: accept the App registration, install it on selected repositories, and return to a Dusk that is reading them.
